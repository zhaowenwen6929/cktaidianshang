## 使用流程
1. 上传商品图（`upload-main`）
2. 选择模式（`mode-choice`：原图精修 / 提取主体精修）
3. 选择创作模式（`creation-mode`：普通 / 高级）
4. 配置高级设置（`advanced-settings`）
5. 填写补充说明（`supplement`，可选）
6. 生成

## 端到端使用流程
1. 用户上传商品图。
2. 用户选择精修模式；若为提取主体精修，再选择提取方式；若为自定义主体，则输入 `customSubject`。
3. 系统识别商品品类、主体类型、边缘质量、背景状态、平台适配倾向。
4. 系统触发 AI Assist，回填 `platformInfo / targetMarket`；若后续接通模式推断，可同步输出 `retouchMode / extractMode / customSubject` 建议。
5. 用户补充特殊约束，或使用 AI 润色把补充说明转成可执行精修要求。
6. 系统按平台规则、品类规则、模式分支、高级选项扩展和输出规格组装最终提示词并提交。

+ `platformInfo`、`targetMarket` 是当前代码里真实存在的高级设置字段。

## 2.1 `ruleLevel` 多规则使用逻辑（同一平台存在多条规则时）
适用场景：一个平台可能同时命中“平台基础规则 + 图位规则 + 风控规则 + 模式规则”。

### 2.1.1 规则定位
+ `ruleLevel=A`：高优先级硬约束，不可被低级规则覆盖。
+ `ruleLevel=B`：稳定通用约束，可被 A 覆盖。
+ `ruleLevel=C`：补充约束，可被 A/B 覆盖，且可在 token 紧张时优先裁剪。

### 2.1.2 组装顺序（强制）
1. 合并所有命中规则的 `required`（去重后全部保留）。
2. 合并所有命中规则的 `forbidden`（去重后全部保留）。
3. `prompt` 按优先级拼接：`A -> B -> C`。
4. 若提示词长度超限，仅从低优先级描述裁剪：先裁 `C.prompt`，再裁 `B.prompt`；`A.prompt`、`required`、`forbidden` 不裁。

### 2.1.3 冲突处理（强制）
+ 若高低级规则存在冲突，按优先级覆盖：`A > B > C`。
+ 若“审美增强”和“真实保真”冲突，永远优先保真。

## 拼装规则
### 拼装顺序
1. `taskGoal`（任务目标）
2. `platformRulePrompt`（平台约束）
3. `categoryRule`（品类约束）
4. `modeRule`（模式分支约束）
5. `parameterLine`（参数行）
6. `optionValuePrompts`（高级选项扩展约束）
7. `requiredRule`（必须满足）
8. `forbiddenRule`（禁止事项）
9. `universalNegative`（通用负向约束）
10. `universalQuality`（通用质量要求）
11. `qualityRule`（精修质量重点）
12. `outputSpec`（输出规格）
13. `supplement`（补充要求，可选）

组装要求：

+ `requiredRule / forbiddenRule / universalNegative / universalQuality` 属于不可裁剪段。
+ token 超限时，仅允许按 `supplement -> optionValuePrompts -> categoryRule -> platformRulePrompt` 顺序裁剪。
+ `retouchMode=original` 时，整段禁止出现“重新构图 / 更换主体 / 替换视角”语义。
+ `retouchMode=extract` 且 `extractMode=custom` 时，`customSubject` 为空必须报错或阻断提交。
+ `resolution` 为空时直接省略该字段，不输出空值占位。

+ 输出结构化 JSON，供字段回填和模式分支判断使用；
+ 判断更适合原图精修还是提取主体精修，而不是只泛化描述“这是一张商品图”。

## 结论
产品精修当前这五块原来都不完整：平台配置、品类配置和高级选项扩展只有概念，没有可开发消费的结构；拼装顺序和模板没有体现真实模式分支；三个关键能力的提示词配置也缺少输入输出协议。

现在这份文档已经补成可直接开发的版本，核心原则是：

1. 平台规则决定“能修到什么程度还算可上架”。
